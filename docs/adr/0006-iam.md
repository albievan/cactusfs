# 0006. Identity and access: policies, API keys, audit trail, Vault

Date: 2026-10-07
Status: accepted

## Context

Until now there was one identity, root, and one rule: root may, nobody else. CLAUDE.md
asks for users, groups, roles and IAM-style policies with default deny; API keys whose
secrets are sealed through the KMS and that never exceed their owner; an append-only,
hash-chained audit trail; console accounts with Argon2id and short-lived sessions; and
Vault Transit as the KMS of clusters. All of it is metadata, so all of it changes the
Raft entry schema and the replicated state.

## Decision

### Model

- A **policy** is a named document in the IAM policy language (`Version`, `Statement`
  with `Effect`, `Action`, `Resource`, `Condition`). A **role** is a named set of
  policies. A **group** holds roles. A **user** belongs to groups and holds roles. An
  **API key** belongs to a user and may carry an inline policy.
- **Parsing is strict.** Unknown fields, `NotAction`/`NotResource`/`Principal`, unknown
  condition operators and keys, a field that appears twice in an object, a field name in
  another case, and a condition block that tests nothing are errors, never ignored: a
  statement that was silently dropped or changed could be the Deny somebody relied on. Actions are `s3:*` and `admin:*` with
  `*` and `?`; resources are `arn:aws:s3:::…` and `arn:cactusfs:admin:::<kind>/<name>`.
  Conditions: `aws:SourceIp` (`IpAddress`, `NotIpAddress`), `aws:SecureTransport`
  (`Bool`), `aws:CurrentTime` (`DateGreaterThan`, `DateLessThan`), `aws:username`
  (string operators). When the source address of a request is unknown, a condition on
  it is decided against the request: it does not hold in an Allow and it holds in a
  Deny. Addresses are compared without zone, IPv4 as IPv4; a policy that writes them
  otherwise is refused.
- **Decision** (`iam.Decide`, the only place it is made): anonymous → no; a node → node
  RPC only; root → everything a user could be allowed; a user → allowed when some policy
  allows and none denies; a key with an inline policy → additionally its own policy must
  allow. An explicit Deny wins. The inline policy can only take away. *Refined by
  [ADR-0028](0028-object-preview.md):* for the one action `admin:PreviewObject`, the
  user who committed the object version asked about counts as allowed when no policy
  speaks of it; a Deny still wins and a key's inline policy must still allow it.
- **Built-in roles** `cluster-admin`, `bucket-admin`, `read-write`, `read-only`,
  `auditor`, each with one built-in policy, are part of the binary, not of the state:
  they mean the same everywhere, cannot be changed or removed, and an upgrade can extend
  them. *Extended by [ADR-0028](0028-object-preview.md):* `bucket-admin`, `read-write`
  and `read-only` hold `admin:PreviewObject`; `cluster-admin` holds it through
  `admin:*`; `auditor` does not.
- **Root stays**, as the identity that sets a deployment up and recovers it. It has no
  policy to lose and cannot be locked out by a mistake in one.

### One consistent read per request

At authentication the key, its owner and every policy document that reaches the owner
are read in one linearizable transaction (`ResolveIdentity`) and travel in the
principal, together with how the request arrived (address, TLS). The authorizer decides
on that, with this node's clock. So a request is judged by one moment's state, costs one
read-index round, and a revoked key, a disabled user or a changed role takes effect with
the next request on every node. The root credential is read once per process: it never
changes.

### In the replicated state

New commands under entry schema version 1 — `iam.user|group|role|policy.put|delete`,
`iam.key.create|delete|touch`, `session.put|delete|expire`, `audit.append` — and new
buckets `users`, `groups`, `roles`, `policies`, `keys`, `sessions`, `audit`. A node of
the previous commit cannot apply these commands; no release has shipped schema version
1, so they are added to it rather than to a version 2 (which is what a released schema
would require, with the rolling-upgrade rule of ADR-0005).

- **The state machine keeps references whole**: a user's groups and roles and a role's
  policies must exist; what is still referred to cannot be removed; removing a user
  removes the user's keys and sessions.
- **It decides nothing that depends on the release.** Which names are built in is a
  property of a binary, so the proposer lists the references it vouches for as built in
  (`known`) and the state machine takes its word. A role or policy a binary cannot find
  contributes nothing when an identity is resolved: what is unknown allows nothing.
- **Secrets.** A key's secret is sealed with a data key that the KMS wraps, bound to the
  access key ID, exactly like the root secret. It is returned once, by the call that
  makes the key. Console passwords are stored as Argon2id PHC strings
  (`m=65536,t=3,p=4`), verified with the parameters in the string. Sessions are stored
  under the SHA-256 of their token; the token and the CSRF token exist only in the
  browser.
- **Last use** of a key is written at most once per key and five minutes, in the
  background.

### Audit trail

Records are numbered without gaps and each carries the SHA-256 of its predecessor
(`internal/domain/audit`); the state machine seals a record onto the chain when it
applies it, so every replica computes the same chain. Nothing removes a record.

- **A change to identities carries its audit record in the same Raft entry.** There is
  no change without its record and no record of a change that did not happen.
- **Refusals** — authorization denials, failed authentications, failed sign-ins, CSRF
  failures — are appended in the background. Anybody can cause them, so they must not
  cost a Raft entry each. The first of a kind is written at once, repeats within ten
  seconds are counted and written as one record. A kind is (actor, action, address) for
  a denial and (action, address) for a failed authentication: nothing the caller can
  vary at will, such as the object named or the key claimed. At most 64 kinds are
  written per window on a node; further ones are counted into one record. Text a client
  controls is cut to 512 bytes and given the hash of the whole, so a record can always
  be written. The queue is bounded; what does not fit is dropped, counted and reported
  in the node's log. A change is never dropped; a record per refusal can be.
- **Other administrative changes** — buckets made and removed, the root credential
  bootstrapped, a topology recorded or a drive replaced, a node registered — are
  recorded right after the change, in the background, not in the same entry: a node
  that stops in between leaves such a change without its record.
- **What a record of a change says**: for a user, the roles, groups and state given;
  for a group or role, its roles or policies; for a policy, the SHA-256 of its
  document; for a key, its ID and whether it expires or is narrowed.
- Reading the trail (`admin:GetAuditLog`) verifies the chain of what it returns and
  fails with an integrity error otherwise. The hash of every new record is also
  published as an event (`cactusfs.audit.recorded.v1`), and `--audit-export` writes the
  records as JSON lines to the log stream: whoever keeps the latest hash elsewhere can
  detect a rewrite of the whole chain, which the chain alone cannot.

### Vault Transit

`--kms vault`: data keys are made on the node and wrapped by Transit `encrypt` with the
caller's associated data, unwrapped by `decrypt` with the same. At start the adapter
proves that it works and that the key binds associated data (an RSA key, say, is
refused). HTTPS is required (plain HTTP only to a loopback IP with `--dev-plaintext`);
the token is read from a file at every use and never logged; redirects and proxies are
not followed. With Vault a cluster needs no shared key file.

## Consequences

- **There is no HTTP surface for IAM yet.** Users and keys are managed through the use
  cases; the admin API (milestone 5) exposes them. Until then the root credential is the
  only way in from outside.
- **A policy can lock everybody but root out**, and root is the way back. Losing the
  root secret of a deployment whose policies are wrong has no remedy yet.
- **Some permissions are as good as all of them.** Whoever may put users may give any
  user any role; whoever may put roles, groups or policies may change what others hold;
  whoever may make keys for an administrator has an administrator's key. Assigning a
  role is not authorized against the role. Among the built-in roles only
  `cluster-admin` has these permissions; a custom policy that grants one of them grants
  the deployment, and should be read that way. The trail records every such change and
  what it granted. A key narrowed by an inline policy cannot make keys.
- **Names that are built in win** over stored ones when an identity is resolved, and a
  stored role or policy cannot take a built-in name. A later release that adds a
  built-in name which a deployment already uses would change what that name means
  there; new built-in names must be checked against that.
- **The state machine validates names by their syntax**, which is part of the format
  and does not change; it validates nothing that a release could decide differently.
- **A changed password does not end the sessions that exist** - *superseded by
  [ADR-0027](0027-session-lock.md): it ends every one of them, at once* - and a user is updated by
  read-modify-write without a compare-and-set: two administrators changing one user at
  the same moment can overwrite each other.
- **A key's last use is recorded when a request's signature verified with it**, not
  when its ID is presented.
- **Audit completeness has a stated limit**: refusals can be dropped under flood, and
  are then only in the node's log. Auditing every successful object read and write is
  not done; the access log is the request log.
- **No lockout or rate limit on sign-in** yet; failed sign-ins cost one Argon2id
  verification each and are audited.
- **Vault tokens are not renewed by the node**, and only token authentication is
  supported: an agent or the platform must keep the token file fresh.
- **Sessions are fixed-length** (30 minutes) and replicated; a session costs one Raft
  entry at sign-in and one at sign-out. *Superseded in part by
  [ADR-0027](0027-session-lock.md):* the length is a setting, and a session that times
  out while its user uploads is locked, not ended - it then costs an entry per third of
  `session-upload-grace` while it uploads.
- Upgrade: a state without the new buckets gets them, empty, when it is opened. Rollback
  to the previous commit is possible until the first IAM command is logged.
